# 动作与授权协议

核心原则：

> **分析 ≠ 授权执行。**

Agent 完成法律分析、生成文书草稿、给出建议，都只是内部工作成果。把成果变成外部行为，需要单独授权。

## 一、需要用户/人工明确授权的动作

以下动作原则上必须获得用户明确授权后才能执行：

```text
- 对外发送（邮件、微信、快递、电子送达等）
- 向法院、仲裁机构、行政机关提交材料
- 正式签署
- 代表客户确认法律或商业立场
- 接受和解
- 放弃权利
- 撤回请求
- 产生费用
- 删除/覆盖正式资料
- 修改正式系统记录
- 创建会产生外部法律效果的动作（提交起诉、申请保全、上诉、申请执行等）
```

## 二、授权确认要素

确认授权时，至少明确：

```text
动作是什么 / 对象是谁 / 方式是什么 / 时机 / 是否可以撤销 / 是否有费用 / 授权人是谁
```

会改变范围、版本、策略、金额、诉请、授权或是否纳入反向案例的选择，同时记入 `用户确认记录`（与 `法律文书出稿前审查` 的 `required_confirmations` 衔接）。

## 三、内部动作的边界

以下动作属于内部工作，不需要外部授权，但仍受其他协议约束：

- 读取已获授权范围内的材料；
- 在系统记录区更新工作笔记、推理记录（按 `post-task-reflection-protocol.md` 与 `matter-workspace-protocol.md` 规则）；
- 生成草稿、预览稿、工作稿（不得标记为正式交付）。

涉及跨事项读取、覆盖已有正式文件、静默写入台账/日历/云文档时，即使属于内部动作，也必须先说明并确认。

## 四、与既有 Gate 的关系

- 合同审查立场确认（`contract-workflow-protocol.md` 第 0 节）、formal delivery Gate、出稿前审查等既有硬闸门继续生效。
- 本协议只提供统一上层规则，不替代既有 Gate。
- 未通过授权检查的动作，一律只输出计划，不得执行。
