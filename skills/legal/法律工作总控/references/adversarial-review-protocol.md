# 反向复核协议（Ludus Adversarial Review）

本协议是 Legal Work OS 的轻量反向复核机制（Ludus Review）。目标只有一个：

> **falsification —— 先尝试推翻当前判断，再允许把它写进正式成果。**

反向复核不是为了显得客观而强行写"一方面……另一方面……"，也不是再分析一遍。它是一次专门以"推翻当前结论"为任务的检查。

## 一、何时触发

普通任务不启动完整反向复核。只有满足以下任一条件时，才执行本协议：

- 存在竞争性事实解释；
- 存在多个合理法律关系或请求权基础；
- 关键事实冲突；
- 证据解释存在实质争议；
- 用户要求诉讼策略、胜诉分析或责任判断；
- 高风险正式成果（正式法律意见、法院提交材料、重大合同/交易、关键诉讼文书）。

简单法律咨询、事实清楚的小额事务、格式性文书等不得启动反向复核；不得为了"显得严谨"制造不存在的争议。

## 二、固定检查清单

对核心判断逐一检查：

```text
1. 用户对法律关系的命名可能错吗？
2. 有没有合理的竞争性事实解释？
3. 对方最强的抗辩是什么？
4. 哪个事实、证据或法律要件一旦失败会推翻结论？
5. 是否存在时效、管辖、主体、程序或举证责任障碍？
```

每一项都必须给出结论：`成立 / 不成立 / 无法检验（缺少哪些材料）`。

禁止这种低价值"复核"：

```text
"仍存在一定风险"
"法院可能有不同观点"
"结果存在不确定性"
```

## 三、Minimum Failure Set

复核者必须回答：使当前结论不成立所需要否定、改变或无法证明的最小条件是什么？

```yaml
failure_conditions:
  - id: FC-001
    condition: 无法证明借款合意
    type: fact            # fact | evidence | law | procedure
    current_support: 仅有转账记录
    weakness: 转账本身无法必然证明款项性质
    impact: fatal         # low | medium | high | fatal
    consequence: 民间借贷关系不成立，诉请基础丧失
    needed: 借条 / 还款承诺 / 明确借款聊天 / 部分还款行为
```

必须指出**具体失败机制**：在哪个要件、因为哪个证据或哪条法条、以什么方式导致结论不成立。

## 四、无实质反例时如实说明

如果检查后没有发现实质反例，明确说明：

```text
未发现足以实质动摇当前判断的反向路径。
```

不得为了"平衡正反"虚构竞争性解释、虚构案例或法条。复核同样遵守 `source-boundary-protocol.md`：测试 hypothetical 时必须显式标识，不得加入已确认事实。

## 五、重度任务的完整对抗（L3）

重大诉讼、正式法律意见、重大交易风险、不可逆程序决定等重度任务（对应 `reasoning-mode-protocol.md` 的 L3），在固定检查之外执行完整对抗：

```text
Advocate → 在已知事实、证据和已核验法律来源边界内，为当前结论构建最强支持论证，
          并逐项暴露薄弱环节（哪些只是当事人陈述、哪些是推断）。

Challenger → 以推翻结论为任务逐项 falsify：最强相反事实解释、最强对方抗辩、
             缺失法律要件、举证责任失败、不利证据、证据真实性/证明力问题、
             相反法律规则、不利案例、相反裁判思路、程序障碍、时效、管辖、
             主体资格、隐藏假设、最小失败条件集合。

反向检索 → 主动检索不利案例、反向法律解释、不同裁判路径、关键例外。
```

三者任务定义必须不同，不能只是"分析两遍"。已形成初步结论时，复核者必须在不承担"维护初步结论"任务的情况下，以推翻该结论为任务；禁止"初步结论 → 找理由证明初步结论 → 再假装反思"。

## 六、输出与记录

- 复核结果：固定检查清单逐项结论 + `failure_conditions` 列表 + 未解决的竞争性解释 + 残余不确定性说明。
- L2/L3 的结构化记录写入当前事项系统记录区 `推理记录/`（见 `reasoning-mode-protocol.md` 持久化分级）。
- 反向检索结果必须进入来源边界记录。
- 复核后是否进入起草，由 `judgment-protocol.md` 的起草许可（PASS / CONDITIONAL / BLOCKED）决定。

## 七、边界

- 本协议只做 Reasoning QA，不替代 Delivery QA（`法律文书出稿前审查`、DOCX 导出、`health_check.py` 等既有硬闸门继续强制生效）。
- 本协议不创建独立 Agent；由当前 Agent 以角色隔离方式执行。
- 不得因通过复核而绕过任何既有交付质量门。
